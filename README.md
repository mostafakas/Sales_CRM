# نظام AL MASTER للموارد البشرية — الإصدار 2.1

بوابة واحدة للموظفين والمديرين والـ HR والمالية: الحضور والانصراف، الأونلاين، الطلبات والموافقات، الإجازات والأرصدة، الجداول، الرواتب والخزينة، والتقارير الشهرية — بهوية AL MASTER (نفس ألوان اللوجو ولوجو الموقع).

> الموقع شغال على نفس مشروع Firebase الحالي (`almaster-b8c18`) ونفس حسابات الموظفين. مفيش build ولا npm: الملفات بترتفع زي ما هي على أي استضافة.

---

## 🔴 لو الموقع بيقول «مش مسموح لك بالعملية دي» أو «Missing or insufficient permissions»
ده معناه إن الموقع الجديد اترفع لكن **قواعد الأمان القديمة لسه هي اللي على Firebase**، والقديمة ما تعرفش مجموعات النظام الجديد فبترفض كل حاجة.
الحل: Firebase Console ← Firestore Database ← **Rules** ← امسح الموجود والصق محتوى `firestore.rules` كله ← **Publish**. بعدها ادخل كأدمن واعمل الترحيل (الخطوة 6).
السيستم نفسه بيظهر شريط تنبيه فوق لو القواعد ما اتنشرتش أو الترحيل ما اتعملش.

## ⚠️ قبل أي حاجة
1. **ألغِ توكن بوت التليجرام القديم** (كان مكتوب صريح في `payroll.html` القديمة): افتح BotFather ← `/revoke`. النظام الجديد مش بيستخدم تليجرام من المتصفح خالص.
2. **جرّب على مشروع تجريبي الأول** (الخطوة 2 تحت). قواعد الأمان الجديدة بتقفل حاجات كانت مفتوحة، ولازم تتأكد إن كل الأدوار شغالة قبل ما تنزل على الحقيقي.

## خطوات التشغيل لأول مرة (بالترتيب)

### 1) نسخة احتياطية
- لو المشروع على خطة **Blaze**: Google Cloud Console ← Firestore ← Import/Export ← Export.
- لو على **Spark**: الترحيل مش بيمسح أي مجموعة قديمة، بس بينقل حقول الراتب والبنك من `users` لمكان محمي ويمسحها من `users` بعد النسخ.

### 2) بيئة تجريبية (مستحسن جداً)
1. اعمل مشروع Firebase جديد (مثلاً `almaster-staging`) وفعّل Authentication (Email/Password) وFirestore.
2. حط الـ config بتاعه مكان الموجود في `assets/js/core/fb.js`.
3. انشر القواعد والفهارس عليه (الخطوة 3)، واعمل حساب أدمن يدوي (الخطوة 5)، وجرّب قائمة «اختبار الصلاحيات» تحت.
4. بعد ما تطمن، رجّع الـ config الأصلي.

### 3) نشر قواعد الأمان والفهارس
```bash
npm install -g firebase-tools
firebase login
firebase use almaster-b8c18
firebase deploy --only firestore:rules,firestore:indexes
```
أو يدوياً: Firebase Console ← Firestore ← Rules ← الصق محتوى `firestore.rules` ← Publish.
(الفهارس: أول مرة استعلام يحتاج فهرس، الكونسول في المتصفح بيطلع لينك ينشئه بضغطة — أو انشر `firestore.indexes.json`.)

> انشر القواعد الجديدة **في نفس وقت** رفع الموقع الجديد. الصفحات القديمة (employee.html, admin.html…) بقت مجرد تحويل للنظام الجديد.

### 4) رفع الموقع
ارفع كل الملفات على نفس الاستضافة الحالية (GitHub Pages أو غيرها)، أو:
```bash
firebase deploy --only hosting
```
الصفحة الرئيسية `index.html` (تسجيل الدخول) والتطبيق `app.html`.

### 5) أول دخول كأدمن
- لازم يكون عندك مستخدم في `users/{الإيميل}` فيه `role: "admin"` (الأدمن الحالي في النظام القديم هيفضل أدمن).
- لو بيئة جديدة فاضية: أنشئ المستخدم من Authentication، وبعدين في Firestore أنشئ مستند `users/<email>` فيه: `name`, `role: "admin"`, `isSuspended: false`.

### 6) ترحيل البيانات القديمة
الإعدادات ← **النظام والترحيل** ← «معاينة» (مش بيكتب حاجة) ← «تنفيذ الترحيل».
بينقل:
| من (القديم) | إلى (الجديد) |
|---|---|
| حقول الراتب والبنك في `users` | `employees_private` (محمي) |
| `hr_stats` + `leaveBalances` | `balances` (رصيد السنة الحالية) |
| `leave_requests` | `requests` (بنفس الحالة) + الأيام المعتمدة الجاية في الجداول |
| `monthly_schedules` | `schedules` |
| `financial_months` | `treasury` (حركات الخزينة) |
| `monthly_finance` | `payroll_items` (أرشيف رواتب قديم) |
| `attendance_override` | `attendance_days` |
| دور `supervisor` | `hr` |
| `leaderEmail` بحروف كبيرة | حروف صغيرة (القواعد بتقارن بالظبط) |
| يوم «شغال» مفتوح من السيستم القديم | بيتقفل (ما كانش متسجل، فمش بيتحسب) |

- التشغيل أكتر من مرة آمن.
- **حساب الغياب بيبدأ من يوم الترحيل** (النظام القديم ما كانش بيحفظ سجل يومي). تقدر تغيّر التاريخ من الإعدادات ← مواعيد العمل.
- صور الإيصالات القديمة (base64) ما اتنقلتش؛ هتلاقي عددها في «ملاحظات» تقرير الترحيل.

### 7) مراجعة الإعدادات
- **مواعيد العمل**: بداية/نهاية الدوام، فترة السماح، أيام الإجازة الأسبوعية.
- **أنواع الإجازات** وعدد أيامها.
- **العطلات الرسمية**: زرار بيضيف العطلات الثابتة، والدينية تضيفها بعد الإعلان.
- **مسارات الموافقة** لكل نوع طلب.
- **قواعد الخصم**: خصم الغياب والتأخير في الرواتب (التأخير مقفول افتراضياً).
- **الموظفين**: راجع الدور والمدير المباشر والراتب وحصة الأونلاين لكل واحد.

## حدود معروفة
- **حذف حساب الدخول نهائياً** محتاج Firebase Console ← Authentication (من غير Cloud Functions). من النظام استخدم «إيقاف الحساب» — بيقفل الدخول فوراً وبيحتفظ بالسجلات.
- **الإشعارات** داخل النظام + إشعار المتصفح. الإيميل والتليجرام من السيرفر والتقرير الشهري التلقائي يوم 1 محتاجين Cloud Functions (خطة Blaze) — دي المرحلة الجاية لو وافقت.
- التقارير الشهرية بتتحسب وقت الفتح، و«إقفال الشهر» بيحفظ نسخة ثابتة.
- قواعد الأمان اتراجعت على كل عمليات الكتابة اللي بيعملها النظام، لكن **ما اتجربتش على Firebase Emulator** (مش متاح في بيئة التطوير) — عشان كده خطوة البيئة التجريبية مهمة.

## اختبار الصلاحيات (على البيئة التجريبية)
- [ ] موظف يبدأ يومه (مكتب/أونلاين) ويغيّر حالته وينهي يومه.
- [ ] موظف يقدّم كل نوع طلب، ويلغي طلب معلّق.
- [ ] المدير يشوف طلبات فريقه بس ويوافق/يرفض، ويعدّل جدول فريقه.
- [ ] HR توافق على إجازة ← الرصيد يتخصم والأيام تظهر في الجدول.
- [ ] HR تضيف موظف جديد ← يدخل بكلمة المرور المؤقتة ويتطلب منه يغيّرها.
- [ ] HR توقف حساب ← صاحبه ميقدرش يدخل.
- [ ] المالية تحسب الرواتب وتعتمدها وتصرفها ← الموظف يشوف قسيمته.
- [ ] من Console المتصفح كموظف: محاولة `updateDoc` على `role` أو على `timeBank` بأرقام كبيرة أو قراءة `employees_private` لموظف تاني ← لازم ترجع `permission-denied`.
- [ ] موظف يفتح `#/employees` أو `#/payroll` ← يتحوّل لصفحته.

### تشغيل الاختبارات محلياً
```bash
pip install playwright && playwright install chromium
python3 tests/flow.py    # المسار الكامل: موظف ← مدير ← HR ← أدمن ← مالية
python3 tests/flow2.py   # إلغاء/رفض/تصحيح/إيقاف/أول دخول/جلسة واحدة
python3 tests/flow3.py   # إلغاء اعتماد + طلب تصحيح
```
الاختبارات بتستبدل Firebase بنسخة محلية في المتصفح (`tests/mock/`) — مش بتلمس بياناتكم.
